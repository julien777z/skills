# Structured player data with ProfileStore

Prefer **[ProfileStore by loleris / Mad Studio](https://github.com/MadStudioRoblox/ProfileStore)** for new structured player-profile persistence. It owns cached profile sessions, periodic saves, and lock handoff between servers. It succeeds ProfileService; the [ProfileService repository](https://github.com/MadStudioRoblox/ProfileService) directs new projects to ProfileStore. The creator's [DevForum announcement](https://devforum.roblox.com/t/profilestore-save-your-player-data-easy-datastore-module/3190543) explains the intended use. It is not a leaderboard or shared, frequently written global-state store.

Pin the chosen upstream release/commit through the project's dependency system and preserve its license. Keep it server-only behind one typed profile service. Inspect existing ownership before replacing persistence: documentation guidance alone does not authorize an unrelated framework migration.

Follow the [official tutorial](https://madstudioroblox.github.io/ProfileStore/tutorial/) for acquiring a session when a player arrives, cancelling when they leave during loading, associating the user ID, reacting to session loss, and ending sessions on departure. Make gameplay wait for a valid profile. Recheck player presence after asynchronous acquisition and release a session acquired after departure. A failed load must never become a default profile saved over unknown data.

Consult the [current API](https://madstudioroblox.github.io/ProfileStore/api/) before integration. Write only during active ownership, without yielding between the ownership check and critical mutation. Do not bypass normal session locks with the steal option. A save request or session-end callback alone is not proof of durable completion; verify the documented saved-data/after-save boundary for teleport handoff. Use Mock for disposable local checks and a separate validation namespace for real save/rejoin tests; these provide different evidence.

Apply the parent skill's MVP policy: validate one current schema and reset incompatible development data or select a fresh development namespace. Do not copy optional reconciliation from an example to preserve obsolete testing records. A quick one-off conversion of allowlisted team testing profiles is permitted outside game code; verify it and remove the script afterward. Do not ship migrations, field backfills, dual formats, or legacy load paths. Distinguish an incompatible record actually read from an unavailable read, and never reset unknown data after a load failure.

For real persistence verification with ProfileStore 1.0.3, assert `ProfileStore.DataStoreState == "Access"` after its bounded initialization. Selecting the non-Mock store alone is insufficient: the library also falls back to an internal mock when Studio API access is unavailable. Keep that failure distinct from a successful durable save. In a dedicated test experience, inspect Studio’s Experience Settings → Security → Enable Studio Access to API Services; re-run in a fresh Play session after the authorized setting is saved. Do not enable access on a live-data experience just to simplify a test.
