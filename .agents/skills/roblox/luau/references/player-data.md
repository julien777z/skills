# Structured player data with ProfileStore

Use **[ProfileStore by loleris / Mad Studio](https://github.com/MadStudioRoblox/ProfileStore)** for structured player profiles, behind one server-side player-data owner. It owns cached profile sessions, periodic saves, and lock handoff between servers. The creator's [DevForum announcement](https://devforum.roblox.com/t/profilestore-save-your-player-data-easy-datastore-module/3190543) explains the intended use. It is not a leaderboard or shared, frequently written global-state store.

Pin a maintained upstream release through the project's dependency manifest and preserve its license. Keep exact resolved commits in the lockfile. Keep it server-only behind one typed profile service.

Follow the [official tutorial](https://madstudioroblox.github.io/ProfileStore/tutorial/) for acquiring a session when a player arrives, cancelling when they leave during loading, associating the user ID, reacting to session loss, and ending sessions on departure. Make gameplay wait for a valid profile. Recheck player presence after asynchronous acquisition and release a session acquired after departure. A failed load must never become a default profile saved over unknown data.

Consult the [current API](https://madstudioroblox.github.io/ProfileStore/api/) before integration. Write only during active ownership, without yielding between the ownership check and critical mutation. Do not bypass normal session locks with the steal option. A save request or session-end callback alone is not proof of durable completion; verify the documented saved-data/after-save boundary for teleport handoff. Use Mock for disposable local checks and a separate validation namespace for real save/rejoin tests; these provide different evidence.

Use versioned, append-only migrations when saved fields are renamed, removed, split, or change meaning. Preserve the project's released data and retention policy. Add defaults and types for a new field; ProfileStore reconciliation fills it for existing profiles. For shape changes, append a migration and test it against the actual earlier shape. Never edit or reorder a shipped migration. Run migrations before reconciliation, keep them self-contained, and reject data from a newer version rather than letting an older server overwrite it. A failed or unavailable read must never become a default profile save. Define the migration API and rollout behavior in the consuming project.

When verifying real persistence with a ProfileStore version that exposes `DataStoreState`, assert it reaches `"Access"` after bounded initialization. Selecting the non-Mock store alone is insufficient when the installed version can fall back to an internal mock after Studio API access fails. Keep that failure distinct from a successful durable save. In a dedicated test experience, inspect Studio’s Experience Settings → Security → Enable Studio Access to API Services; re-run in a fresh Play session after the authorized setting is saved. Do not enable access on a live-data experience just to simplify a test.
